# Byte Core 0.1.0

Byte Core 0.1.0 is the planned first functional self-managed release. This note is included now only to make candidate artifacts reproducible; it does not announce a release or authorize a tag.

The candidate contains the dependency-light lifecycle CLI, canonical deployment templates, exact-plan install/update/removal proofs, optional Bash and Zsh integration, local-first Byte Care diagnostics, and repository-native Codex guidance.

Experimental configurable helpers add a separate deployment-owned TOML file, navigation and assistant launch/resume shortcuts, Git status, optional prompt/history/highlighting/aliases, exact-plan configured Git synchronization, numeric-IP reachability, and direct or SSH-relayed wake requests. They do not import deployment-specific shortcuts, launch applications while validating settings, discover targets automatically, or publish repositories. Third-party highlighting requires a fresh shell to undo; wake results do not verify power state. See `docs/helpers.md` for settings and remaining manual validation.

Optional guided setup now checks prepared helper settings and local prerequisites, plans a new destination, creates the exact validated TOML bytes with mode `0600` after full plan-ID approval, and verifies the result. It never overwrites existing settings, installs dependencies, edits profiles, or launches configured applications. Shell loading and operational helper use remain separately reviewed steps; see `docs/setup.md`.

The internal layered resolver enforces deployment-relative workspace-path syntax and provides read-only containment resolution against an explicit deployment root. Version-2 shell plans now verify profile mode and bind selected shell-source checksums and modes, including the packaged native Bash/Zsh asset. Old shell plans must be regenerated. The advisory SessionStart hook safely handles malformed source fields, including arrays and objects, with generic fallback guidance.

Optional guided inventory adds exact Nmap discovery/inspection plans, bounded execution, offline XML import, exact-model lookup in explicit cited capability catalogs, and reviewed deployment-owned snapshots. No background discovery, automatic model web research, device configuration, or manifest rewrite is provided. Live network and manufacturer evidence remain unvalidated; see `docs/inventory.md`.

The repository guidance includes a reusable GitHub workflow in `docs/github-workflow.md`: prepare scoped changes with current documentation, verify the reviewed PR commit and checks, preserve authorization boundaries, and clean up integrated branches with recovery evidence. This is shipped assistant guidance, not an automated GitHub command or a grant of repository access.

The fork's `docs/fork-divergence.md` indexes intentional local differences for optional upstream review. Repository and contribution guidance require keeping its public-safe summaries, validation, and verified disposition current. The log is packaged documentation, not an automatic tracker, upstream acceptance record, or grant of publication authority.

The source checkout also includes an optional Ubuntu 24.04 x86_64 dev-container recipe and disposable candidate smoke test. This development tooling is excluded from the release artifact and does not establish native platform support evidence.

Source-only `scripts/setup_byte_core.py` adds guided local candidate installation and starter initialization with explicit paths, a Python version preflight, saved private plans, approval of both full plan IDs, and verification after each apply. The script also checks the actual POSIX launcher, including its `python3` and Git on `PATH` and host support, before preparation and after approval; a failed or timed-out launcher check refuses setup with prerequisite guidance. It preserves preparation and partial state for review; it provides no combined rollback, dependency installation, shell changes, or release acceptance evidence. See the first-session guide for arguments and recovery boundaries.

Known limitations:

- support is limited to the host matrix recorded in `docs/support-matrix.md`;
- remote update discovery and automatic diagnostic reporting are unavailable;
- enterprise fleet management, multi-administrator policy, and paid features are outside v0.1;
- elevated installation and package-manager integration are not provided; and
- the release remains blocked until all automated and manual release-gate evidence passes.

Kubuntu 26.04 x86_64 detection and fixture coverage are implemented under [issue #36](https://github.com/kodiakdirus/byte-core/issues/36). Recognition requires explicit flavor metadata or installed Kubuntu desktop package evidence; plain Ubuntu 26.04 remains unsupported. No native Kubuntu hosted runner or passed native lifecycle record is claimed. The release checker requires four platform records plus the independent fresh-user review, all currently pending.

Remaining implementation limits are documented in the configuration, setup, shell integration, Byte Care, and Codex integration contracts under `docs/`: workspace resolution and shell verification are point-in-time checks, shell source binding does not recursively cover arbitrary imports or the helper launcher/backend, diagnostics report a fixed bootstrap version and use bounded issue deduplication, and live Codex hook behavior still needs manual evidence. Configuration setup preserves existing files and does not manage later edits or automate their deletion.
